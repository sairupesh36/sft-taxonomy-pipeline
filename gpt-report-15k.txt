# Final SFT Sample Mapping Audit

## Semantic correctness + JSONL line-level review

**File audited:** `sft_output_sample_mapped.jsonl`
**Total records:** 15,722
**Audit objective:** determine whether the generated taxonomy mapping semantically represents the user's actual SFT task, while checking tool, interaction, composition, IO, constraints, and response behavior.

---

# 1. Executive verdict

## Overall rating: **7.9 / 10**

This is **good**, and I would continue using the taxonomy.

I would **not** call the mappings ground truth yet.

The strongest parts are:

* basic domain mapping
* ordinary QA
* mathematics
* straightforward code generation
* healthcare
* legal
* retrieval
* IO metadata
* response behavior
* agent/tool detection

The biggest remaining problems are:

1. **programming-problem datasets are often classified as mathematics/reasoning**
2. **reasoning scratchpad is still being treated as a tool**
3. **some simple tasks are incorrectly marked composed / multi-turn**
4. **tool usage is sometimes inferred without evidence**
5. **secondary task labels are occasionally inflated**
6. **timezone conversion is being called unit conversion**
7. **capability limitation is sometimes paired with `declined_request`**
8. **domain/subdomain sometimes follows the reasoning technique instead of the substantive task**
9. **task_subfamily still mixes multiple conceptual dimensions**

## ERROR 1 — Programming problem classified as pure mathematics

### JSONL line: **11494**

**User task:**

An airport control-tower programming problem involving runway lanes, divisibility, selecting aircraft, and input constraints.

**Current mapping:**

```text
domain:
    mathematics

task_family:
    calculation

domain_subdomain:
    discrete_mathematics

task_subfamily:
    algebraic_and_symbolic_calculation

tool_category:
    reasoning_scratchpad
```

### Verdict: ❌ WRONG

This is a programming/algorithmic problem.

The presence of mathematical constraints does **not** make the SFT task a mathematics calculation task.

If the expected output is code, the primary classification should be closer to:

```text
domain:
    software_engineering

task_family:
    code_generation

domain_subdomain:
    general_purpose_programming

task_subfamily:
    algorithmic_problem_solving
```

Then, separately, you could have:

```text
reasoning_type:
    discrete_optimization / combinatorial
```

This is one of the most important recurring errors in the final sample.

# 27. The biggest recurring error in the whole sample

After looking across the final-SFT data, this is the thing I would prioritize above everything else:

## **Programming problem ≠ mathematics task**

Your mapper is repeatedly doing:

```text mathematical structure
        ↓
mathematics
```

when it should sometimes do:

```text requested artifact = code
        ↓
software_engineering / code_generation

mathematical structure
        ↓
secondary reasoning/problem characteristic
```

This is especially visible in the `code_pipeline_team2` section.

That means this isn't one accidental misclassification.

It is a **systemic mapper rule problem**.

---

# 28. The second biggest recurring error

## `reasoning_scratchpad` is not a tool

Your current final data has:

### **6,077 / 15,722 records**

containing `reasoning_scratchpad` in `tool_category`.

That's approximately:

## **38.6% of the entire sample**

That is much too high.

Your tool distribution becomes misleading.

For example:

```text tool_category:
    reasoning_scratchpad
```

doesn't tell a downstream consumer that the dataset uses an external tool.

It tells them only that the sample contains or was processed with some reasoning representation.

Those are different things.

### I would remove this category from `tool_category` entirely.

---

# 29. Third biggest issue

## `task_subfamily` is doing too much

You're currently putting things like:

```text factoid_qa
closed_domain_qa
open_domain_qa
multi_hop_qa
logical_deduction
step_by_step_walkthrough
function_generation
```

inside the same layer.

But these describe different properties.

For example:

```text factoid_qa
```

= answer/task type

```text closed_domain_qa
```

= grounding

```text multi_hop_qa
```

= reasoning structure

```text step_by_step_walkthrough
```

= response style

Those should not necessarily compete as a single taxonomy dimension.

# 42. What I would change in Claude Code now

I would put these rules directly into the mapper:

```text
RULE 1:
Identify the requested output/task before identifying the subject matter.

RULE 2:
If the user asks to write/implement/debug code,
code-related task family takes precedence over mathematical
or scientific reasoning labels.

RULE 3:
Mathematical concepts may be represented as reasoning/problem characteristics,
but they do not automatically define the primary task domain.

RULE 4:
Logical deduction does not imply mathematics.

RULE 5:
Constraints do not imply proof_and_formal_reasoning.

RULE 6:
Assistant execution method must never redefine the user task.

RULE 7:
Internal reasoning/scratchpad is not a tool.

RULE 8:
Only assign a secondary task if it corresponds to an independently
requested user objective.

RULE 9:
Tool requirement describes what is necessary.
tools_used describes what actually happened.

RULE 10:
Capability limitation is not the same as policy refusal.

RULE 11:
Clarification required is not a refusal.

RULE 12:
Timezone conversion is distinct from unit conversion.

RULE 13:
Do not infer tool usage from the mere possibility of using a tool.

RULE 14:
Atomic means one user objective, even if solving it requires many reasoning steps.

RULE 15:
Composed means the user requested multiple independently meaningful objectives.
```
