I went through the **full 1,000-sample file**, not just the first 20 or a convenient subset. The file contains **87,262 lines**, and all 1,000 `MAPPED RESULT` objects were parsed and audited. 

I’m going to be blunt because this is exactly the stage where being polite would actually hurt the project.

# My verdict

### Your taxonomy design: **8/10**

### Your current mapping quality: **5.5/10**

### Production readiness of the mapper: **4/10**

### Potential after fixing the mapper: **8.5–9/10**

The important distinction is:

> **Your taxonomy is substantially better than your mapper's current behavior.**

I do **not** think you need to throw away the taxonomy.

I **do** think you need to substantially change the mapping logic.

The biggest problem isn't that the taxonomy lacks categories. The biggest problem is that the mapper is **not consistently understanding what exactly is being classified**.

And there are some genuinely nasty examples in this 1,000-sample set.

# 1. The biggest problem: the mapper is sometimes classifying the ANSWER instead of the TASK

This is the single most important finding.

Your taxonomy should primarily answer:

> **"What task is this SFT example asking the model to perform?"**

But several mappings behave as if the question is:

> **"What did the assistant happen to output?"**

Those are very different things.

### Example: idx 264

The user asks where they can learn about fair-use guidelines for a YouTube book-review video.

That's fundamentally:

* legal
* copyright / intellectual property
* information seeking / QA / retrieval

But the assistant bizarrely answers in rhyme.

Your mapper labels it:

* `domain = legal`
* `task_family = generation`
* `subfamily = creative_generation`

The `legal` part is good.

The **generation / creative_generation part is wrong if you're classifying the underlying SFT task**. The user didn't ask for a poem. The model independently decided to answer as a poem. 

This is exactly the kind of example that exposes the problem.

### Correct interpretation

I'd map the task more like:

```text
domain:
  legal

domain_subdomain:
  intellectual_property

task_family:
  question_answering
  or search_and_retrieval

task_subfamily:
  open_domain_qa
  / legal_information_qa
```

Then separately:

```text
response_behavior:
  answer
```

or, if you want to capture what actually happened:

```text
response_style:
  creative_style
```

But **creative generation should not replace the underlying task**.

# 2. Refusals are destroying your domain mapping

This is another major issue.

Take idx 375.

The user asks for a detailed clandestine chemistry laboratory setup for illicit drug production.

The assistant refuses.

Your mapper produces:

```text
domain = general
task_family = generation
domain_subdomain = general_assistance
task_subfamily = text_generation
```

That's a poor representation of the actual task. 

The underlying task is clearly chemistry / illicit drug production / laboratory procedure.

The fact that the assistant refused does **not** magically turn the user's task into "general assistance."

This is where I strongly recommend adding a separate axis:

```text
response_behavior:
    normal_answer
    refusal
    partial_refusal
    safe_redirection
    tool_error
    unable_to_answer
```

Then the same example can be represented as:

```text
domain:
    pharmaceuticals_and_life_sciences / science_and_research

task_family:
    generation

task_subfamily:
    procedural_generation

safety:
    restricted_harmful_request

response_behavior:
    refusal
```

Now you preserve both pieces of information.

Your current mapping is throwing away the **actual task identity** because the model refused.

That's bad for SFT analysis.

# 9. Your `task_subfamily` layer mixes different dimensions

This is subtle, but very important.

Look at your QA labels:

```text
factoid_qa
closed_domain_qa
open_domain_qa
multi_hop_qa
conversational_qa
```

These aren't all the same kind of property.

For example:

### `open_domain`

describes **knowledge grounding**

### `closed_domain`

also describes **knowledge grounding**

### `multi_hop`

describes **reasoning structure**

### `factoid`

describes **answer type**

### `conversational`

describes **interaction style**

You're currently putting all of them into one `task_subfamily` bucket.

That's why you end up with things like:

```json
"task_subfamily": [
    "multi_hop_qa",
    "open_domain_qa"
]
```

That combination is actually telling you something useful.

But you're forcing two dimensions into one field.

# 11. `task_composition` is actually pretty decent

This part surprised me.

You have:

```text

```

That overall distribution looks plausible.

And I don't think you should define:

> composed = multiple task families

That's too restrictive.

A task can be composed while remaining within one family.

For example:

```text

```

with:

```text

```

is composed even if the overarching task family is still tool use.

So your current instinct here is good.

### But define it explicitly:

**Atomic**

> one independently meaningful task objective.

**Composed**

> two or more dependent/independent subtasks required to fulfill the user's objective.

Don't derive it merely from:

* number of sentences
* number of labels
* number of tools
* prompt length.

# 12. Complexity is being contaminated by prompt scaffolding

You have:

```text
single_step = 512
multi_step = 456
complex_workflow = 32
```

The problem is that `complex_workflow` appears to sometimes describe the **benchmark wrapper**, rather than the underlying task.

The Mbabane question is a good example.

The user asks one final question, but because the agent performs several web searches, it sometimes becomes:

```text
complex_workflow
```

That's defensible if complexity means **execution complexity**.

But then a simple customer-support question can also become a complex workflow because the surrounding agent policy/tool environment is complicated.

That's dangerous.

You need to define complexity around the **required work**, not the length of the system prompt.

I'd use:

```text
single_step
multi_step
complex_workflow
```

based on the minimum number/structure of operations required to complete the user's goal.

Not based on:

> "this prompt had a 100-line system policy, therefore complex."

Humans have already invented enough bureaucracy without teaching the taxonomy to reproduce it.

# 20. I would NOT make every field LLM-generated

Some fields should be deterministic.

For example:

### Output format

If the assistant output is:

```json
{"answer": "..."}
```

you can detect JSON.

If:

```sql
SELECT ...
```

you can detect SQL.

If Python code:

```python
def ...
```

you can detect PY.

Don't waste expensive reasoning tokens asking an LLM what format a string is.

Same for:

* language
* number of turns
* number of tool calls
* whether tools were actually invoked
* whether output contains code
* whether user explicitly requested JSON
* whether there are numbered subtasks.

Use code.

Save LLM reasoning for semantic decisions.



That rule would fix many examples.

# 27. Priority ranking of problems

If you're going to fix this with Claude Code, don't randomly tweak labels. Do it in this order.

### 🔴 P0: Fix task-vs-response classification

The mapper must classify:

> **what the user asked**

not:

> what the assistant happened to produce.

This alone will fix a huge number of errors.

---

### 🔴 P0: Add response behavior

Especially:

```text
refusal
partial_refusal
safe_redirection
tool_failure
normal_answer
```

This prevents refusals from corrupting domain/task labels.

---

### 🔴 P0: Make mapping deterministic

Run the same example multiple times.

If:

```text
temperature = 0
```

still gives different labels, your prompt/schema is underspecified.

Use explicit decision rules.

---

### 🔴 P1: Split task-subfamily dimensions

Separate:

```text
QA type
reasoning depth
grounding type
answer type
```

Don't cram them together.

---

### 🔴 P1: Fix browser/computer-use taxonomy

Don't map browser navigation to:

```text
frontend_development
```

You need a browser/computer-use category.

---

### 🔴 P1: Reduce `other`

`other` should mean:

> **the taxonomy genuinely has no suitable category.**

It should NOT mean:

> the mapper wasn't confident.

Those are completely different things.

---

### 🟠 P2: Separate primary/secondary domain

This will clean up your multi-domain mappings.

---

### 🟠 P2: Separate tool requirement from tool execution

This will clean up your tool-heavy SFT data enormously.

---

### 🟠 P2: Deterministically derive IO metadata

Don't spend LLM reasoning on JSON detection.

# 28. The most important metric you should add

Forget raw accuracy for a second.

For this kind of taxonomy mapper, I want:

## **Mapping Consistency Rate**

Take identical examples.

Run them through the mapper 5 times.

Then calculate:

```text
same_mapping / total_runs
```

You want:

```text
>99%
```

for easy examples.

And then:

## **Hierarchy Consistency**

Check:

```text
domain → valid subdomain
task_family → valid subfamily
tool_requirement → valid tool_category
```

No impossible combinations.

And:

## **Ambiguity Rate**

```text
examples requiring human adjudication
/
total examples
```

This should ideally become small.

* browsing
* agentic tasks
* safety/refusal
* multi-domain tasks
* structured outputs
* database agents
* retrieval
* reasoning

That's a strong foundation.

The problem is that your current mapper is trying to make a **single semantic judgment across too many independent dimensions at once**.

That's why it occasionally produces beautiful mappings and occasionally decides that a web-navigation task is frontend development because humanity apparently needed one more reason to suffer.

# 30. My final honest assessment

If you asked me:

> **"Can I use these 1,000 mappings as ground truth for training another model right now?"**

### **No.**

I would **not** use them as ground truth yet.

There is too much label noise and too much inconsistency.

The biggest evidence is the identical-context repetitions. The same regenerative-farming example appears 29 times with substantially different taxonomy outputs, and the Mbabane task likewise changes domain/task interpretation across repetitions.  

But:

> **"Should I abandon the taxonomy?"**

### Also no.

I'd keep roughly **80–90% of the conceptual architecture** and rebuild the mapping engine around it.

Your next iteration should be:

```text
RAW SFT SAMPLE
      ↓
Understand user objective
      ↓
Determine primary task
      ↓
Determine domain
      ↓
Determine orthogonal facets
      ↓
Determine tool dependency
      ↓
Determine complexity/composition
      ↓
Determine constraints
      ↓
Determine response behavior
      ↓
Validate hierarchy
      ↓
Confidence / ambiguity
      ↓
FINAL MAPPING
```

And crucially:

```text
                 ┌── task identity
RAW SAMPLE ──────┼── domain identity
                 ├── execution/tool metadata
                 ├── reasoning metadata
                 └── response behavior
```

**Don't let one label contaminate another.**

That is the core architectural lesson from these 1,000 samples.
